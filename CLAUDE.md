## Next.js version caveat

This project is on **Next.js 16.4 / React 19.3**, which differs from older App Router conventions.
`AGENTS.md` (generated by `next dev`) requires reading the relevant guide in
`node_modules/next/dist/docs/` before writing framework code. Specifics already relied on here:

- `next.config.ts` enables `cacheComponents: true` and `partialPrefetching: true`.
- `PageProps<"/[lang]/work/[slug]">` and `LayoutProps<"/[lang]">` are **globally generated**
  types — do not import them. `params` is a Promise and must be awaited.
- `src/proxy.ts` is the Next 16 replacement for `middleware.ts` (exported function named `proxy`).
- `export const instant = false` in `src/app/[lang]/work/[slug]/page.tsx` opts that segment out of
  instant-navigation validation (see `node_modules/next/dist/docs/01-app/02-guides/instant-navigation.md`).
- Tailwind v4 is wired through Turbopack (`turbopack.rules` in `next.config.ts` maps `*.css` to
  `@tailwindcss/turbopack`). There is no `tailwind.config.js` and no PostCSS config.

`AGENTS.md` is rewritten by `next dev`; commit it alongside your changes rather than reverting it.

## Architecture

A single-person portfolio site in three languages. Everything is statically rendered from in-repo
data — no CMS, no API routes, no database, no client-side data fetching. All 28 routes are
prerendered at build time.

### Content vs. structure

`src/data/` holds **locale-independent structure only**; every translatable string lives in
`src/i18n/dictionaries/`. The two are joined by a key:

- `work.ts` — `CaseStudy[]` with a `slug` (closed union `CaseSlug`) and `stack` (tech names, same
  in every locale). Adding a case study means extending `CaseSlug`, adding the entry, adding a
  `case` branch in `CaseHero` (its switch has no `default`, so TypeScript flags the gap), and
  filling `cases[slug]` in all three dictionaries.
- `projects.ts` — `Project[]` keyed by a closed `ProjectId` union, with `category`, `year`,
  `image`, `href`. Entries are currently placeholders.
- `site.ts` — email, phone, LinkedIn, CV path. Not translated. Exports a derived `phoneHref`.

### Routes

All pages live under `src/app/[lang]/`: `/` (work list), `/projects`, `/about`, and
`/work/[slug]`. The case page derives its `NN / NN` counter and "next project" link from the
entry's index in the `work` array. `globals.css` and `favicon.ico` stay at `src/app/`.

### Composition

Every page is `<PageShell>` (main + spacer + `<Footer>`) wrapping `<ProfileHeader />` and
`<Tabs active="…" />`. `Tabs` owns the nav list and its `TabKey` union; each page passes its own
key rather than reading the pathname.

`ProjectsGrid` (filter state) and `LocaleSwitcher` (`usePathname`) are the **only** `"use client"`
components. Keep everything else a Server Component.

## Internationalization

Locales are `en` / `ru` / `kk`, declared in `src/i18n/config.ts`. **English is served from the
root**: `/about` and `/ru/about` both exist, `/en/about` 307s to `/about`. `src/proxy.ts` does
the rewrite and the redirect; its matcher skips `_next/`, `images/` and anything with a file
extension.

- Server Components read the locale with `getI18n()` (`src/i18n/dictionary.ts`), which resolves
  `[lang]` through `next/root-params` — no prop drilling. It cannot be called from Client
  Components, Server Actions or Route Handlers, so client components take translated strings as
  props (see how `ProjectsGrid` receives `t` and `locale`).
- Build internal hrefs with `withLocale(locale, path)`; it returns the path unchanged for the
  default locale. `stripLocale` is its inverse, used by `LocaleSwitcher`.
- `src/i18n/types.ts` defines `Dictionary` explicitly (rather than inferring from `en`), so a
  missing case slug, project id or key fails the build in all three dictionaries.
- `{placeholder}` substitution goes through `fill()`; counts go through `plural()`, which uses
  `Intl.PluralRules` — Russian needs `one`/`few`/`many`, Kazakh only `other`
  (`src/i18n/format.ts`).
- Person and company names are kept in Latin in every locale; the name is a dictionary key if that
  should change.

## Styling conventions

Tailwind v4 only — utility classes in JSX, no CSS modules, no inline `style`.
All colors are CSS custom properties in `src/app/globals.css`, exposed to Tailwind via
`@theme inline` (`--color-ink` → `text-ink`/`bg-ink`/`border-ink`). Add a new color by defining
it in `:root` **and** mapping it in `@theme inline`; brand colors for case heroes follow the
`--globerce` / `--jaryq-bg` naming.

Two fonts are loaded in `[lang]/layout.tsx` via `next/font/google` and exposed as CSS variables
consumed by the `.font-primary` (IBM Plex Mono, the body default) and `.font-display` (Unbounded)
base classes — not by Tailwind font utilities. IBM Plex Mono needs the `cyrillic-ext` subset:
Google's `cyrillic` subset stops at U+45F and omits the Kazakh letters Ә Ғ Қ Ң Ү Ө Һ.

The design is uppercase monospace at a small base size (`text-[13px]`, `tracking-[0.6px]`),
centered in a ~500–520px column. Copy is written uppercase in the dictionaries themselves rather
than with `text-transform`.
